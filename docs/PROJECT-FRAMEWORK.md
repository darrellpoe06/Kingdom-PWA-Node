## 1. Vision

SKOS — the Sovereign Kingdom Operating System — is the **Sovereign Family Financial OS**, prebuilt for the many roles a real family carries: steward of the home, of the children, of the books, of the doors, of the small business, of the practice, of the ministry, of the contractor relationship, of the tenant relationship, of the inheritance to come. It is engineered as a **cross-domain experiential-knowledge counselor marketplace** so that the experienced — pastors, elders, lay counselors, ministry leaders, business mentors, Scripture teachers, technology counselors, and more — can come alongside families in the domains in which they have actually walked, rather than only in the domains for which they hold credentials. The intellectual spine is **The Holy Spirit Integration Worldview**: *"The Holy Spirit's work in a Sovereign believer is integration — Him in us and us in Him, by the Spirit, through Christ, to the Father — and the integrated life is the relationship; everything else, including the receiving of what is asked, flows from it as fruit"* (`docs/00-foundations/_root/THE-HOLY-SPIRIT-INTEGRATION-WORLDVIEW.md`). Every module serves this. Every decision is filtered through it.

- Tier: Community · Families in Need (free, sponsored).

- Tier: Community Partners · Organizations (free, verified annually).

## 9. Update protocol

Every working session in this repository follows this protocol. It is binding, not advisory.

**At the end of every working session, before close, commit an update to this file that includes:**

- A **dated entry** in §7 (Recent decisions log) for anything decided that day, however small. If nothing was decided, write that — "no decisions today, work was X" — so the log is continuous.
- Any change to §5 (Current state — branches and PRs): branches created/deleted, PRs opened/merged/closed, CI state changes, what shipped, what's blocked. Re-run `git status` and `git branch -a` (and, when available, `gh pr list`) to verify reality before writing.
- Any change to §6 (Active workstreams): next-step changes, owner changes, status changes (in-flight / blocked / done).
- Any change to §8 (Open questions): mark answered ones resolved (move to §7 with the resolution date), add new ones surfaced during the session.
- If a foundation doc was created, modified, or moved during the session, reflect it in §2.
- If a module was added, status-changed, or moved between live/planned/vision, reflect it in §3.

**At the start of every working session, before any other action:**

- Read this file end-to-end.
- Skim the relevant foundations doc(s) named in §2 for the workstream being touched today.
- If §5 reports something stale (a PR that's now merged, a branch that's gone), update it before opening new work.

The point is that a year from now, the chain of decisions, the chain of branch-state, and the chain of open questions are all readable in one place. No archaeology. The living spine carries the context so the work does not have to re-discover it.
