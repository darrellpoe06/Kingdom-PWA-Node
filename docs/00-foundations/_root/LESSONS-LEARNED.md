# LESSONS-LEARNED

**Foundation doc, Layer 3 (reference).** Comprehensive historical record of every incident, near-miss, surprise, and discovery that taught the PoeTech build something it didn't know before. Companion to `EXECUTION-OUTCOME-OBSERVABILITY` (which catches the failures) and `INSTITUTIONAL-MEMORY-EVENTS` (which structures them as data). This doc holds the human-readable narrative + the extracted principle.

Per Darrell 2026-06-03 evening: "Lessons learned area for comprehensive historical records." Established as a Layer 3 foundation so every future session inherits the institutional learning without having to rediscover it. The four binding-principle memories that produced this doc (in order of relevance):

- `project-institutional-memory-events` — every fix / pipeline issue / decision / principle becomes first-class structured data
- `project-execution-outcome-observability` — every workflow execution outcome must be observable AND alerted on
- `feedback-research-first` — research before shipping, not after
- `feedback-known-savings-must-ship-same-session` — when a lesson IS the saving, it ships immediately

## Purpose

A lesson is not the same as a fix. A fix solves the specific case. A lesson distills WHY the case happened, WHAT FAILED, and WHAT MUST CHANGE STRUCTURALLY so the class of failure can't recur. The fix lives in the master fix list + the commit; the lesson lives here so future sessions, future engineers, future stewards inherit understanding rather than re-discover the failure.

Three uses of this doc going forward:
1. **Onboarding artifact** — any new collaborator (Christiana, future contractors, future Foundation Agent) reads this to understand the lived history.
2. **Architectural reference** — when a new feature is being designed, the relevant lessons here are consulted FIRST so the design accounts for what's already been learned.
3. **Quality-Gatekeeper input** — wf36 reads new lessons and updates its pre-merge checks accordingly.

## Schema (every entry)

```
### YYYY-MM-DD — Incident Title

**Trigger:** what the user / system / monitor was doing when it surfaced.
**Detection path:** who/what noticed, and when in the timeline.
**Detection delay:** time between problem starting and human awareness — flag if > 0 min.
**Investigation steps:** chronological list of what was tried, in order.
**Root cause(s):** the actual mechanism(s) — can be multiple; name each.
**What worked:** the move(s) that produced the fix.
**What didn't work:** attempted moves that LOOKED like they should fix but didn't, and why.
**Principle(s) extracted:** the distilled rule(s) for future similar cases. Each is a single sentence.
**Forward architectural fix:** the structural change that closes this class of failure, not just this instance.
**Observability gap (if any):** what n8n / monitoring / the AI Foundation should have caught but didn't.
**Cross-refs:** related memories, commits, foundation docs.
```

Lessons accumulate top-down (newest first). Older entries are not removed; they are sometimes amended with "→ revised understanding YYYY-MM-DD" lines when later evidence sharpens the principle.

## Principles Extracted (running index — populated from incidents below)

These are the distilled, binding lessons. Each links back to the dated incident(s) it was extracted from. Future Claude sessions read THIS section first when designing new surfaces:

- **P1 — Defense layers must cover ALL data paths, not just the most-visible one.** A gate on one webhook doesn't help when localStorage / sessionStorage / IndexedDB / SW cache hydrate the rest of the app independently. (Extracted: 2026-06-03 localStorage leak.)
- **P2 — Service Workers are silent staleness multipliers.** Any "ship a fix" pipeline must include explicit SW version-bump + cache invalidation, or the fix never reaches users behind a cached SW. (Extracted: 2026-06-03 localStorage leak.)
- **P3 — Production outcome verification, not just deploy verification.** "Vercel says ready" + "n8n says workflows active" ≠ "fix actually fixed it." Every fix needs a synthetic probe that LOADS the live surface from a CLEAN context and asserts the new behavior. (Extracted: 2026-06-03 localStorage leak; 2026-06-03 wf13 noise persistence.)
- **P4 — Marking a fix "verified" requires testing in the FAILURE MODE, not the clean state.** A demo-mode test pass tells you the demo path works; it does NOT tell you the localStorage-already-populated path works. Test in the conditions the bug appeared in. (Extracted: 2026-06-03 D17 "verified" status that masked the larger leak.)
- **P5 — Outcome observability is the missing layer between system observability and product correctness.** n8n knows the system is up; it does NOT know what the live product is RENDERING. Every binding mission test (the four ethical tests + the Father's Business test) needs a SYNTHETIC that asserts the product still passes from a fresh visitor's perspective. (Extracted: 2026-06-03 localStorage leak.)
- **P6 — Repeated "NOT FIXED" without root-cause escalation wastes attention.** When a fix lands but the symptom persists, the NEXT investigation must escalate depth (DOM inspection → JS state → localStorage → SW → CDN → DNS), not iterate at the same surface layer. Each failed retry is signal that the model of the system is incomplete. (Extracted: 2026-06-03 localStorage leak — multiple "shipped" commits before root-cause was actually identified.)
- **P7 — Research before shipping; don't interpret-and-ship.** When a user message is short, the temptation to interpret quickly and ship a code change is the failure mode `feedback-research-first` was written to prevent. Confirm the interpretation, surface the alternatives, then ship. (Extracted: 2026-06-03 wf27 evening-only misinterpretation; reinforces existing feedback memory.)
- **P8 — `default-now-asap` for outbound communication; research-first for code changes.** These two binding principles don't conflict — send the user what's ready immediately, BUT before generating new code changes, research the actual user intent + the existing system state. The asymmetry: communication latency hurts the user's 5-minute windows; code-change latency saves the user from interpret-and-ship regressions. (Extracted: 2026-06-03 same-day pairing of `feedback-default-now-asap` + `feedback-research-first` reinforcement.)
- **P9 — Distinguish data leaks from brand presence.** Real-ops-data (real entity names, addresses, project titles in app state) is a leak. Real-business-brand advertising (Poe Properties / TLC Therapy Solutions in the family-ministries carousel) is intentional. Sanitization passes must NOT touch brand surfaces; only data surfaces. (Extracted: 2026-06-03 localStorage leak; reinforces `feedback-distinguish-data-from-brand`.)
- **P10 — Autonomous timer-driven automation needs three brakes before it ships active: a budget, a concurrency lock, and a kill-switch.** A token/turn/wall-clock ceiling per run, single-instance locking so a new fire skips rather than stacks on a hung one, and a dead-man's-switch that auto-pauses on overrun instead of auto-continuing. Without all three, a hung or looping run burns compute until a human kills it by hand. (Extracted: 2026-06-06 autonomous-automation runaway.)
- **P11 — Nothing self-activates unattended, least of all while the principal is away.** Automation that spawns more automation — or more Claude/compute — on a clock is shipped inactive and turned on only with someone watching. "Ship it live" during a vacation window is the exact condition that converts a small loop into an unrecoverable runaway. (Extracted: 2026-06-06 autonomous-automation runaway.)
- **P12 — Automation that consumes compute on a timer is Tier C, never Tier A.** The "NAS-only sovereign surface = Tier A" and "additive = Tier A" shortcuts do not apply to anything that runs on a schedule; sovereignty of location and additiveness of code do not bound cost or blast radius. (Extracted: 2026-06-06 autonomous-automation runaway.)
- **P14 — Auth changes the trust boundary; a leak gate for anonymous visitors must not lock out authenticated owners.** The 2026-06-03 public-host gate (rightly) forced demo data for ANYONE on poetech.us — but it kept doing so after sign-in, so the family used their own app staring at fake "Reeves/Maya/Jordan" data, feedback evaporated on refresh (persistence blocked), and the sync path could even upload demo rows into their real cloud instance. Reported by Christina + Darrell 2026-06-11 ("can't tell when I'm logged in… fake data mixed with ours"). Fix: anonymous = demo + no hydration + no persistence (gate stands); authenticated owner = own data hydrates, persists after hydration completes, and demo-only record ids are provenance-filtered out of every upload and every cloud-loaded list. Corollary: **any auto-upload path must filter by data provenance** — sample/demo rows never sync. (Extracted: 2026-06-11 signed-in-but-fake-data incident; pairs with P1/P9.) → revised understanding 2026-06-11 evening: the sweep itself missed the one UN-GATED sync path (entities), which had already pushed demo rows into the cloud — a provenance sweep enumerates every sync path and ends with a cloud-table audit, not a code read. → second revision, same night: the 2026-06-03 "public host = never" rule was copy-pasted into at least FOUR independent gates (snapshot hydration, `importedAllowed`, Imported.jsx's self-guard, the boot-time profile read) — when auth semantics change, grep every `isPublicHost()` / host-check call site and apply the owner-exception to ALL of them in one pass, or the surface fails one layer at a time across the whole evening.
- **P13 — Schema files are not applied state; verify the live catalog before mapping code to columns.** A migration file in the repo proves intent, not application. `CREATE TABLE IF NOT EXISTS` silently no-ops against a same-named table from an earlier generation, leaving a hybrid: the old shape with the new triggers. Before writing any sync/mapping code, query `information_schema.columns` (and pg_constraint / pg_trigger) on the LIVE database and map to what is actually there. (Extracted: 2026-06-10 phantom-v2.2-rentals discovery.)
- **P15 — A surface is a live view of, and a control for, real system state — never a static depiction of it.** Every number, status, date, or "% complete" on a surface must trace to real work (a real record, a real run, a real timestamp). If it can't be traced, it doesn't ship — a painted number is worse than no number on a surface whose whole value is trust. The app is where the flow RUNS, not where it is drawn. (Extracted: 2026-06-13 — the Build board was a hand-typed constant in a file; it could not show a real % complete because nothing real fed it, and it would not flag its own missed target until accountability was wired.)
- **P16 — Reality-trace before building any surface (the "a human would have known" gate).** Before writing code for a surface: (1) name the real data and the real screen it touches; (2) confirm it connects end-to-end in the LIVE system, not the demo; (3) confirm it is the surface the user ACTUALLY uses — by observing the running app, not by assumption; (4) state these assumptions out loud first, so a wrong premise is caught in a sentence (cheap) rather than after a merged PR (expensive + trust-eroding). (Extracted: 2026-06-13 — screenshot upload was built into the small "What do you see?" widget when the form in use was the "Tell us what you think" modal; and "drive the Build board from the projects table" was a premise error — the Build board is platform data, not the user's projects — caught by running the trace BEFORE coding.)
- **P17 — n8n Code nodes: no global `fetch`, and `require('http')` is DISALLOWED. The only HTTP that works is `this.helpers.httpRequest`.** `require('fs')` IS allowed (used for reading secret files). Anything in a Code node doing `fetch(...)` or `require('http')` fails — `fetch` silently if it's in a try/catch (e.g., wf30's ntfy push has been quietly failing), `require('http')` loudly ("Module 'http' is disallowed"). Sweep all Code-node HTTP onto `this.helpers.httpRequest`. (Extracted: 2026-06-13 — the live workflow-status feed lost hours cycling through "fetch is not defined" → "Module 'http' is disallowed" before `this.helpers.httpRequest` worked.)
- **P18 — Infra behind a private LAN (home/church NAS) cannot be reached by a CLOUD agent — its network egress is allowlisted shut. LAN-bound work runs on a LOCAL agent or via an API the cloud can reach; never by turning the human into the agent's hands for dozens of manual UI steps.** A cloud Claude Code session gets "Host not in allowlist" hitting a Tailscale Funnel; the fix is Claude Code on a machine ON that LAN (it has native LAN/Tailscale access), driving the change over an API. Verify reachability first (the agent pings the LAN IP) before assuming it can act. (Extracted: 2026-06-13 — a cloud session directed ~hours of manual NAS clicking it could have done itself from a local agent over the n8n REST API.)
- **P19 — In n8n, the Executions tab shows code + output AS IT RAN (a historical snapshot), not the editor's current code; and "Succeeded" only means "did not throw," not "returned the right thing."** A node returning `{ok:false, error:...}` still shows a green "Succeeded." Debugging stalls when a stale execution snapshot looks like the current code, or a green badge hides an `ok:false` payload. Diagnose live behavior from the **Editor** + a **fresh** run, and read the actual OUTPUT — never trust the badge or an old execution view. (Extracted: 2026-06-13 — long detours from reading stale execution snapshots and "Succeeded"-but-ok:false runs.)
- **P20 — Identity and personalization are part of the tenancy boundary; gate them on VERIFIED membership, not on the mere presence of a session.** Real family names, the family device-picker, "whose device is this" — all leaked to a signed-in NON-family user because they were gated on `authSession` being truthy ("is anyone signed in?") instead of `isFamilyEmail` ("is this a family member?"). A non-family account is still an account: it has a session, so a session-only gate treats a parishioner as family. Gate identity on the same membership signal that gates data; give an outside signed-in user their own self-serve profile (`'self'`), never the family surface. (Extracted: 2026-06-14 — a parishioner saw "Darrell" at the top and was locked out by a family-only picker; sharpens P14, which fixed data hydration but not identity.)
- **P22 — A green pipeline run must mean the target state MOVED; "recorded my own failure" is not progress.** transcript-backfill run #2 exited 0 and printed "the % climbs now" while fetching 0/135 transcripts — every request was IP-blocked, and the script counted "wrote an error row" as advancement, so the stall-guard never tripped. A success path must be defined by the outcome the run exists to produce (rows with real text landed), not by the absence of a crash; an all-blocked run exits non-zero. Sibling of P19 ("Succeeded" only means "did not throw") applied to CI. (Extracted: 2026-07-02 transcript-backfill false green.)
- **P23 — Never record an environmental failure as a durable fact about the data.** The blocked fetches were written into `video_transcripts.error` as no-caption verdicts, so every future run — CI and NAS alike — would skip those 126 videos as "already resolved": a transient runner condition (YouTube blocks GitHub's datacenter IPs) was converted into permanent false state. Classify before persisting: only an exception that states a fact about the ITEM (captions disabled, video gone) may be stored as a resolved verdict; a fact about the RUNNER (IP block, network failure) writes nothing and is retried. Skip logic keys off verdicts only, which also self-heals any mis-recorded rows. (Extracted: 2026-07-02 transcript-backfill false green; pairs with P4 — the failure mode to test is the blocked runner, not the happy path.)
- **P27 — A "not found yet" is not a "never will exist"; age-gate before recording an ABSENCE as a durable verdict.** YouTube takes a couple of days (longer for long services) to auto-generate a new upload's captions, so the loader fetching an hours-old sermon got `TranscriptsDisabled`/`NoTranscriptFound` — the SAME error class as a genuinely caption-less video — and recorded it as a permanent no-caption verdict. Because the corpus is fetched newest-first, a `--max` backfill would stamp exactly THIS WEEK's sermons (the ones the church most wants) permanently caption-less and route them to a Whisper fallback that may never run, even though the captions would appear a day or two later. This is P23's sibling on the other axis: P23 says don't persist a RUNNER failure as a fact about the item; P27 says don't persist a TIMING condition (too-new) as a fact about the item either. Fix: gate the verdict on the video's age (`choir_sermons.service_date`) — a no-caption result inside a ~4-day grace window is transient (retry later), only an OLDER video's absence is durable; a recent video carrying a premature verdict is re-fetched so it SELF-HEALS once captions land. The human knew this (Darrell: "there's not closed captions for that video yet... takes a couple days"); the system now knows it too, as a proven-to-catch CI gate. (Extracted: 2026-07-06 — a 12h-old "Celebrate!" sermon returned TranscriptsDisabled during the caption backfill; pairs with P23; guarded by `infra/nas-sme-pipeline/test_load_transcripts.py`.)
- **P34 — A `cancel-in-progress` concurrency that covers a job which also runs a HEAL wait-loop will CANCEL the heal during rapid events — scope concurrency per-job (supersede the sweep, never the heal).** The auto-merge deploy/migrate heal (the P25 GITHUB_TOKEN-push-gap dispatch, made race-proof with a wait-loop 2026-07-14) lived in the same workflow as the enable-sweep, under a WORKFLOW-LEVEL `concurrency: {group: auto-merge-sweep, cancel-in-progress: true}`. That flag is correct for the enable-sweep (only the newest matters — idempotent) but it cancels the ENTIRE run, so during rapid successive merges (2026-07-18 night: ~8 PRs back-to-back) each new sweep killed the previous run's in-flight deploy wait-loop mid-poll, and the deploy never dispatched — every merge had to be hand-dispatched, the exact hands-off-delivery failure DR-0103 exists to prevent. The heal only ever survived in a quiet stretch. Fix (2026-07-19): split into two jobs with PER-JOB concurrency — `enable-auto-merge` supersedes (cancel-in-progress: true), `heal` NEVER cancels (cancel-in-progress: false, its own group, runs independently), so its wait-loop always runs to completion. Honest co-cause: the observing agent also PREEMPTED the automation, hand-dispatching within ~1-2 min of each merge before the 6-min wait-loop / 5-min freshness cron could fire — so part of the "it never auto-deploys" impression was impatience, not the gap; the real, structural defect is the cancellation. Governed by P26 (a lane change is NOT done until a real merge produces a real deploy with NO hand-dispatch — the proof for this fix is the NEXT merge after it lands). (Extracted: 2026-07-19 — "Fix the automerge automation"; Darrell's prompt to read the Ways first is what surfaced that the heal already existed and the real bug was the concurrency scope. Pairs with P25 (the dispatch), the 2026-07-14 wait-loop lesson (win the race), P26/DR-0107 (prove the deploy).)
- **P26 — A DOWN or STALE production site is the WORST outcome; uptime outranks delivery velocity, and a merge/CI/deploy-lane change is NOT "done" until a real merge has produced a real deploy.** On 2026-07-06 the agent enabled the auto-merge lane (DR-0103) and poetech.us went stale for ~9 hours — the site the family and COLG depend on — because the deploy silently stopped firing. This was a BAD decision by the agent, recorded plainly so it is remembered: the identical failure mode was **already documented six lines away in the very file being edited** (the db-migrate GITHUB_TOKEN patch), and the agent shipped the lane change without checking whether the deploy path had the same gap. CI-green is NOT deploy-proof. Binding correction: when you touch auto-merge / CI / the deploy workflow, enumerate every downstream `push`-triggered effect and PROVE each still fires by watching a real merge deploy — before calling it shipped. Any doubt about the live site outranks any velocity gain. A locked front door makes all the speed behind it worthless. (Extracted: 2026-07-06 — auto-merge went live without verifying the deploy survived it; the worst outcome, a down site, resulted. Governs with DR-0107.)
- **P28 — A turn NEVER ends with an authorized increment parked "for a fresh stretch": start it, or arm the wake that continues it — self-granted deferral is undermining.** The agent had a verified build map, standing consent, an explicit "we need that asap," and a given timeline — and still ended the turn with the increment unstarted, citing its own long session as the reason ("the disciplined call is a fresh stretch"), with NO wake armed and no re-review date. That is not prudence; it is the agent usurping the governor's scheduling authority (the DR-0111 failure class in a new costume: parking instead of re-asking). The rule: context length / "fatigue" is NEVER a stop signal the agent may grant itself — compaction exists and carries the work. If the agent genuinely believes quality is at risk, it SAYS so and CONTINUES unless the governor says park; a legitimate park carries the DR-0075 form (why + re-review date) AND an armed wake. The ways-review (DR-0108) now asks: "did any turn end with an authorized increment unstarted and no wake armed?" (Extracted: 2026-07-07 — Darrell: "Nothing got done!" then "Underminer... make sure you can't undermine us in the same way or other ways." Execution took ~45 minutes once started; the FAMILY'S wall clock — request 05:55Z to finish 12:17Z — was 6.4 hours, overnight. The wall clock is the report metric [Darrell's correction], recorded in the delay ledger.)
- **P25 — Enabling auto-merge silences EVERY `push:<branch>` workflow — audit and explicitly dispatch each one.** A GITHUB_TOKEN-driven merge (native auto-merge armed by the token) pushes to `main`, and GitHub suppresses `push`-triggered runs from GITHUB_TOKEN (anti-recursion). So the instant auto-merge goes live, every `on: push: branches:[main]` workflow — deploy, migrate, any post-merge automation — stops firing, silently: the PR still merges green, so nothing looks wrong while production freezes on the last HUMAN-merged build. When you turn on auto-merge, enumerate every `push:main` workflow and dispatch each from the auto-merge job via `workflow run` (the one token action GitHub does NOT suppress), gated so one merge = one run. (Extracted: 2026-07-06 — poetech.us froze on build 6bfae29 for hours after auto-merge (DR-0103) went live; the SAME gap had already broken cloud migrations / the Choir tab on 2026-06-16, was patched for db-migrate ONLY, and the deploy workflow was left exposed. Pairs with P22/P3: a green merge that never deploys is a false green.)
- **P24 — After completing agreed-to work, DEFAULT TO MOTION; do not end a turn by asking the principal to re-authorize what standing consent already covers.** When the next step is an authorized continuation — finishing the delivery loop, watching the PR you opened, pulling the next backlog item (DR-0089 standing consent, DR-0103 §4 move-without-being-pushed, Drive-Don't-Delegate) — DO it and report it; a trailing "should I watch, or keep going?" re-imposes the exact push the streamlined loop exists to remove. Ask ONLY when the next step is a genuinely NEW decision, a discovered premise conflict, a standing-rule/bright-line conflict, or a Tier-C governance gate (the DR-0089 carve-outs) — and then as a recommendation with a default, never a bare either/or menu. (Extracted: 2026-07-06 — after "both," the agent shipped both then asked "watch PR #613 or pull #2 forward?", handing back a decision the standing rules already made.)
- **P21 — Run the RLS reality test before calling a suspected exposure a breach: a name on screen is not a data read.** When a user reports seeing someone else's identity/data, compare what `service_role` (RLS bypassed) returns against what the unauthorized identity's OWN path returns (anon key, or a non-member token), with exact row counts (`Prefer: count=exact`). If the unauthorized path is 401/blocked/empty on every data table while service_role sees rows, RLS is holding and the on-screen artifact is cosmetic (a hardcoded/cached string), not a leak. The panic cost of "my family data is exposed" is real and so is the cost of dismissing a real leak — the test resolves which in minutes. Pair it with the user's own ground truth (their feedback screenshot shows literally what they saw). (Extracted: 2026-06-14 — "Darrell at the top" was a hardcoded `PROFILES` string; the RLS test + Jayden's screenshot proved no data crossed instances; sharpens P9 in the auth direction.)

- **P30 — Reviews that verify the SURFACE renders live data do not verify the DATA is being tended; a live view of an untended queue is still stale.** Four record surfaces failed the same day the same way (2026-07-07): boards absent from the timelines with no phase-completion context, a feedback promote queue holding month-old tester notes, Discussions at zero "Ari notes" while dozens of decisions shipped, concerns days past their targets — and every one had passed the standing checks, because the checks (P15/P16, DR-0076) assert "real rows, no painted numbers," not "the rows are being worked." The staleness was in the WORKFLOW, not the pixels. Structural close (DR-0120): (1) where a ripple can be DERIVED it is — finishing a phase's last item writes its own timeline-context entry in the same write, so no one has to remember; (2) every queue surface states in-surface how long its items have waited (queue-freshness), so an unworked queue can never look fine; (3) tending the app's record surfaces as features land is an ASSIGNED responsibility (the Local LLM lane, per Darrell; the build agent ships structural ripples + honest seeds until that lane is live); (4) the ways-review asks "which record surfaces did this work outrun?" (Extracted: 2026-07-07 — the four-screenshot stale-tabs sitting; governs with DR-0120. P15's second half: a live view is necessary; a tended flow is sufficient.)

- **P31 — Deploy-green is not site-up; the site is proven from OUTSIDE, on a clock, or downtime has no witness.** On 2026-07-08 Darrell reported the app down while every deploy run in the ledger was green — and "how many times today?" had no measured answer, because every safeguard watched the pipeline (CI proves the build; the healers prove a deploy was dispatched) and NOTHING ever made an HTTP request to the site the family opens. Worse, the observing agent's own sandbox had no route to the site (egress policy), so the blindness was doubled: no instrument, and no eye. The close (DR-0125): an outside-in scheduled probe (a GitHub runner is the team's vantage point — WAYS-REVIEW: the agent's limits never bound the team) measures up + intact + fresh with browser-shaped requests every ~10 min, files every failing observation on the rolling `incident` issue (the queryable downtime ledger), heals a stale build, and renders live in the app beside the lane state. Sibling of P26 (a down/stale site is the worst outcome) and P5 (outcome observability): P26 says prove the DEPLOY; P31 says prove the SITE — they are different proofs, and only the second one answers the family's question. (Extracted: 2026-07-08 — "down again!!!! How many times today?"; first probe run also caught its own extraction bug reading "unknown" as fresh — fixed so unknown NEVER reads as fresh, DR-0076.)

- **P32 — A deploy is not atomic at the domain edge: the window where the new shell answers before its assets is a real outage class, and a missing asset must NEVER answer 200-HTML.** Twice measured on 2026-07-10 (boot-check runs 29081767095 / 29082532512): for ~7–12 minutes after an upload, poetech.us served the NEW index.html while its hashed chunks were not yet reachable at the domain layer — each missing chunk fell through to the SPA fallback and answered `200 text/html`, the browser refused HTML-as-module, zero JavaScript ran, and the family photographed a blank page (Darrell, 09:03Z, inside the first window). pages.dev served the same deployment green throughout, which localized the fault to the custom-domain layer. The per-build chunk stamp (P-class fix from #715) made this WORSE-shaped: every deploy renames every chunk, so the moment the new shell lands, no old asset can satisfy it. The two truths to hold together: the witness instruments told the story exactly (boot-check named the wrong-mime file; site-health proved recovery between windows — P31 working as designed), and the durable fix is a serve-layer decision (missing assets answer 404 so chunk-reload-heal can act, or a zone cache purge rides the deploy) — recorded on incident #722, decision `re-review: 2026-07-12`. **CLOSED 2026-07-10 by DR-0155:** the root was worse than a window — the fallback HTML was stamped `immutable` by request-path `_headers` and poisoned the browser cache, the edge, and the SW asset cache for the life of the deploy (why every heal rung and "one more tap" kept failing on a device that hit the window). The asset guard (`app/functions/poetech-app/assets/[[path]].js`) now answers any non-asset for an asset path as `404 no-store` (proven-to-catch in `asset-guard.test.js`), and verify-boot measures each deploy's real propagation window on the run summary before judging boot. (Extracted: 2026-07-10 — "I CANT DOWNLOAD THE POETECH APP WHY"; the download failure's first face was this window, not the install chain.)


- **P33 — A gate must stand where the user stands: a fresh browser's first visit is never service-worker-controlled, so a broken worker fetch handler is invisible to every first-visit instrument while it kills every INSTALLED device.** On 2026-07-10, 8 minutes after #750 shipped a cache-first shell, every family phone showed ERR_FAILED on every visit ("All PoeTech Apps Moore and Mines") — while CI, the deploy run, verify-boot, and site-health were all green, because each one judges a first contact and the family lives on the Nth. The mechanism (reproduced locally both directions): install's `cache.add` follows Pages' `/index.html` → `/` 301 and stores a `redirected` response; a browser refuses a redirected response for a navigation. The close (DR-0160): revert-first per DR-0107/P26 (heal proven before promised — sw.js fetches bypass the broken handler, one no-store visit swaps the worker), then TWO instruments that stand where the devices stand: sw-nav-check in required CI (Cloudflare-shaped serve, two visits, worker control REQUIRED before judging) and boot-check's second controlled pass on the real domain. The sibling lesson learned building them: BOTH gates' first drafts passed the broken worker — one never registered a worker (vacuous), one closed its page mid-check (a bare `return` before a `finally`) — so the standing rule sharpened: a gate ships only after it is run against the known-broken artifact and CATCHES it (DR-0076 §3, now with two more proofs). 1. **The P14 provenance sweep covered the verify-gated numeric-table block and missed the `entities` block** — the ONLY table that syncs un-gated at sign-in, and therefore the only path that could pollute or re-render pollution. The sweep enumerated the visible block, not every sync path.
2. **The public-host mount puts the demo dataset into state before auth resolves**, so the sign-in `initialSync` uploaded whatever demo entities were on screen.
3. **"Verified" never included a cloud-table audit** (P3/P4 again): the demo rows were already in the cloud and no probe ever SELECTed them.
**What worked:** timestamped SELECT as receipts before any delete; filtering BOTH directions (`localList.filter(notDemoRow)` on upload, `merged/items.filter(notDemoRow)` on pull) plus skipping entities sync entirely in demo mode; postgres-role `DELETE ... RETURNING` in Studio (4 rows, slugs + names + instance shown); clean-device re-verify on the redeployed preview (4 entities, all real).
**What didn't work:** deleting via the client session's REST call — `entities` has no RLS DELETE policy, so PostgREST returned **200 with 0 rows deleted**. A silent no-op that looks like success.
**Principle(s) extracted:** P14 corollary sharpened — a provenance sweep must enumerate EVERY sync path, gated AND un-gated, and it is not "verified" until the cloud table itself has been read; the un-gated path is precisely the one that bites. Secondary: an RLS table without a DELETE policy returns 200/empty on DELETE — treat 0-rows-returned as failure, not success.
**Forward architectural fix:** entities block filtered both directions + demo-mode skip (PR #24, commit 6e0070b); cloud strays deleted with receipts. KNOWN RESIDUAL: production (main) still runs the unfiltered upload until PR #24 merges — signing in on poetech.us before the merge re-uploads `e-family`; accepted, the merge is the close.

### 2026-06-06 — Autonomous timer-driven automation ran away and required a manual shutdown

**Trigger:** A fleet of always-on, timer-driven automation shipped `active` on 2026-06-02/03 right before Darrell left for Maui — the wf27+wf31 continuous-feedback reel (5-minute cron, commit `e969693` / fix-list D23), the wf-autonomous-builder (`active: true`, 30-minute cron, whose purpose is to start Cowork/Claude build sessions), the Ollama `keep_alive` model-pin, the wf42 batch queue, plus five scheduled Cowork tasks (hourly snapshot + four check-ins, each spawning a Claude session). **Detection delay:** ~hours-to-days. The `poetech-hourly-snapshot` task wrote a file every hour through 2026-06-06 13:10 Central, then stopped cold — no 06-07 or 06-08 snapshot exists. That gap is the failure window; awareness came only once the runaway was already bad enough to require a manual kill.

**Investigation steps (this session, 2026-06-08):**
1. Repo + snapshot review showed the hourly-snapshot heartbeat stopping at 06-06 13:10 Central with a ~2.3-day gap.
2. Identified the suspect surface from the working tree: the 5-min reel, the autonomous builder (active), the keepalive model-pin, the batch queue, and the five scheduled tasks — all designed to run unattended on timers.
3. Confirmed the failure mode from Darrell: runaway compute + looping/repeating + hung — NOT rogue infra actions (no unwanted changes to the NAS/n8n).
4. `list_scheduled_tasks` returned zero tasks → the fleet had already been torn down by hand. That deletion WAS the "manual shutdown."

**Root cause(s):**
1. **Primary: autonomous timer-driven automation shipped with none of the three brakes** — no token/turn/wall-clock budget (a hung run burned indefinitely), no single-instance concurrency lock (a new timer fire could stack on top of a hung one), no kill-switch / dead-man's-switch (the fleet auto-continued when it should have auto-paused).

3. **Tertiary: shipped active during a vacation window** — the one person who would notice was traveling. The 2026-06-02 "ship it live" directive removed the human supervisor at exactly the wrong moment.
4. **Quaternary: treated as low-risk / Tier A** — "NAS-only sovereign" + "additive" reasoning routed compute-on-a-timer changes straight to active with no soak and no budget.

**What worked:** Manual deletion of the scheduled-task fleet stopped the runaway. Read-only forensics (snapshot gap + working-tree artifacts + scheduler state) reconstructed the mechanism after the fact.

**What didn't work:** Nothing automated stopped it — there was no budget cap, no lock, no auto-pause. The every-5-min wf27 cron had ALREADY been reverted once on 06-03 (commit `d3657d6`) for being too aggressive; the pressure returned via the keepalive model-pin and the still-active builder. A one-off revert did not generalize into a standing rule, so the class of failure recurred.

**Principle(s) extracted:** P10, P11, P12 (see Principles index above).

**Forward architectural fix:**
1. **Binding guardrail (shipped with this entry):** no autonomous timer-driven automation ships without a budget + concurrency lock + kill-switch; that class is Tier C, never Tier A. Added to `CLAUDE.md` ("Autonomous Automation Requires Three Brakes") and `RELEASE-TIERS.md` (Tier C list + flowchart Q1).
2. **Quarantine (shipped with this entry):** the uncommitted re-arm artifacts (`wf-autonomous-builder.json`, `42-batch-research-queue.json`, and the builder/keepalive/batch apply scripts) moved to `docs/00-foundations/_quarantine/` with a README; NOT to be applied until the Cage (PR #5) is merged AND each carries the three brakes.

Extend that same budget / health-gate / auto-stop discipline to the Claude-orchestration layer (scheduled tasks + the autonomous builder), not only to network/VLAN actions.
4. **Single-instance lock + max-runtime on every scheduled task** before any of them is recreated: a new fire that finds a prior run still going skips rather than stacks, and a run that overruns its window terminates.

**Observability gap:** No budget/cost monitor and no "task overran its window" alert existed. The snapshot heartbeat stopping was the only signal, and it was passive (an absent file), not an alert. A dead-man's-switch that fires when the heartbeat stops, plus an aggregate compute/cost ceiling that auto-pauses the fleet, are the missing pieces.

**Trigger:** Darrell, on vacation in Maui, opened poetech.us and saw the Books → Imported tab showing real Chase transactions; the Big Picture dashboard rendering real ops data (1508 Holly Hill, Christiana college transition, 805 Apt 2 furnace, Holy Spirit Integration Worldview · finish + KDP, Poe Properties, TLC Therapy Solutions). **Investigation steps:**

2. Hypothesized: Darrell's "incognito" test was actually on a non-incognito tab on his own device, where localStorage carried his profile forward → `currentProfile=darrell` → gate passed → tab unlocked.
