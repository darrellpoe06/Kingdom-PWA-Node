## Context

Direct messages have been sealed end to end since 2026-07-25 (0118): each user generated an ECDH P-256 keypair in the browser, the private half stayed in that browser's `localStorage`, and the public half was published to `dm_public_keys`, **one row per user**. A pair key derived between my private key and their published public key sealed each body (`e2e:v1`).

The module's own header stated the limit: a message is readable only on the device holding the key. What the header did not say is what happens when a person has more than one device, which Darrell does (a phone, a desktop, the Fold, the tower).

## What was measured

- **The code.** `dm-encryption.js` has not changed since 2026-07-25; `direct-messages-sync.js`'s sealing path has not changed since then either (the commits since touched push reporting, the thread's space, and `requireEncryption`). No "previous fix" altered which messages open; the flip is the design's own behavior.
- **The mechanism.** `publishDmPublicKey()` upserts `{ user_id, public_jwk }` on `user_id`. Every device that opens Messages generates its own keypair and publishes it **over** the last one. A sender's phone derives the pair key from the recipient's *current* published key, so a message is sealed to whichever of the recipient's devices published most recently. On the recipient's other devices it reads *Encrypted message — it can only be read on the device that holds the key.* Which messages a given phone can open therefore **flips** every time another of the person's devices opens Messages, and the sender's own earlier messages flip too (the pair key they were sealed under changes when the recipient's published key changes).
- **The live database** (sovereign-read `dm_keys`, 2026-10-01 13:46 UTC, run 36870626287, no bodies and no keys printed): 15 accounts hold a published key; Shay (`737f5d3b`) to Darrell's phone account (`c2a6c39a`) sent 2 sealed messages on 2026-10-01 at 13:11 UTC, the two shown locked in his screenshot, and 1 on 2026-09-23 at 13:01 UTC, shown open. The v1 table's `updated_at` is the first publish, not the last (the upsert never touched it), so it cannot date the overwrite; the fingerprint column now makes the next change visible.
- **What a device can and cannot open, by construction.** A device holds only the keys it generated. Nothing can make a device open a message that was sealed before that device existed, without moving a private key between devices; that is a key-transport road and is not built here.

## Impact

Before: a person with two devices had messages that opened on one and not the other, changing which with no visible cause, and the only words on screen blamed "the device that holds the key". After: a message is sealed once and its content key is wrapped for **every device of both people**, so it opens on each of the recipient's devices and on the sender's own other devices; a device that joined Messages later is told, in words, that the older messages were sealed for the other devices before it joined, and it opens everything sent after.

## Decision

1. **One public key per device.** Migration 0249 adds `dm_device_keys (user_id, device_id, public_jwk, label, last_seen_at)`, primary key `(user_id, device_id)`. The device id is the same per-browser id `device-trust.js` keeps (`poe-device-id`). Any signed-in person reads every device key (a sender needs every device of the recipient); only the owner publishes, re-publishes or forgets their own rows; anon reads none.
2. **Sealed for every device.** `sealForDevices` encrypts the body once under a fresh AES-256-GCM content key and wraps that key, under the ECDH pair key between the sending device and each receiving device, once per device of both people: every device of the recipient, every device of the sender, this device included. Wire: `e2e:v2:<base64 json>` carrying who sealed it (`user:device`), the body, and the wraps. The private key still never leaves the device.
3. **Opened on this device, or said why not.** `openDmShape` finds this device's wrap, derives the pair key with the sending device's public key, unwraps, and decrypts. No wrap for this device shows *Sealed for your other devices before this one joined Messages — new messages open here.* A v1 body is tried against every public key of the other person we know (the v1 row and each device key), so it opens wherever its key is held; one that cannot be opened keeps the v1 words.
4. **The v1 row is still published** (the device's latest key), so an app that has not yet updated seals v1 to it; a recipient with only a v1 row receives a v1 body. The v1 road is left in place, not removed.
5. **The devices are on the screen.** Under a thread, Messages lists the devices the person's messages open on, marks this one, and offers *Forget* for each other device, so a phone no longer held is sealed for no longer.
6. **The walls are proven on a real PostgreSQL in CI** as a required leg (`dm-device-keys`), the same shape as 0247's and 0248's smokes.
7. **The evidence read is kept** (`sovereign-read dm_keys`, #1936): a key fingerprint and date per account, sealed and plain counts per day per pair; never a body, never a key.
