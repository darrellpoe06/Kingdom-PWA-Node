## Context

`renumber-decision-record.mjs` has said since DR-1021 that *"The pointer is left to resolve-ledger-conflicts.mjs, which already owns it."* Its bare-id rewrite is a whole-file `DR-nnnn(?!\d)` replace, and `INDEX.md` is one of the files it rewrites.

## What was measured

**The sentence was false for as long as it has been written.** On a fixture, moving 1355 → 1362: `**Next ID:** DR-1355.` became `**Next ID:** DR-1362.`

**The alignment is the normal one, not a rare one.** A session takes the number the pointer names, finds another session took it first, and renumbers off it — so the pointer holds exactly the number being moved almost every time this tool runs. The pm15 builder hit it on #2567 today, where the pointer it wrote named that session's own new record.

**And the case that pinned the contract could not fail.** `leaves the pointer to the resolver that owns it` has been green throughout, because its fixture put the pointer on DR-1018 while moving DR-1016 — the one input where the bug has no number to match. A green check that cannot catch its subject is the anti-theater failure DR-0076 §3 names, and this is one, in a case written to prove exactly the thing that was broken.

## Impact

Two sessions have now had a renumber falsify prose: yesterday an already-merged session note stating what the pointer *had been* set to, and today the pointer itself. Both are statements about a value, rewritten because they contained a number.

## Decision

**1. The rewrite is line-wise and the pointer line is held back** by a `POINTER_LINE` predicate. Everything else is unchanged: the row still relinks, the heading still moves, citations elsewhere still move.

**2. A mention left standing in that line is REPORTED, never fixed.** Rewriting it was considered and refused, because the annotations there come in two shapes this tool cannot tell apart: *"DR-1344 was taken on 2026-11-05"* is history and stays true after the record moves; *"DR-1016 = a-gospel-with-a-hole-in-it"* describes the current state and goes stale. Rewriting the first is precisely yesterday's fault. So it is named for the operator, the way an ambiguous citation already is in this same tool.

**3. A pre-existing assertion is narrowed, not deleted.** `expect(index).not.toContain('DR-1016')` claimed the whole file loses the old id; the truthful claim is that the ROWS do. It now reads the rows.

## Verification

**36 cases green** (32 before, +4), and 62 with the resolver's own suite beside it.

**Proven to catch.** Removing the one `skipLine` guard turns **3 cases red**, including the new real-run case that reads what the tool actually printed rather than asserting the behaviour in prose. File restored and verified byte-identical with `cmp`. Lint clean.

**Not claimed:** that this prevents a renumber from falsifying prose anywhere else. It fixes the pointer line specifically. Every other line a renumber touches is still rewritten by number, which is correct for a citation and wrong for a statement about a past value, and telling those apart is not something a regex can do. `re-review: 2026-11-20`.
