## 3. Part A: Marketplace architecture

### 3.0 The question, restated

Darrell asked the right question precisely: *"the ability to add the internet functionality like square or is it better to integrate with a vendor."* The answer this review reaches is a third path he also named in the same breath -- *"we add any vendors we want based on what and who does the best and whenever they change we want the ability to keep records and we can change the vendors"* -- which is neither "be Square" nor "marry one vendor," but **own the spine and treat every vendor as swappable.** That requirement (vendor-swap with a full audit trail) is the single fact that decides the architecture.

### 3.1 The three paths compared

#### Path 1 -- Square (turnkey SaaS payments + commerce)

**What it is.** A unified payments + commerce stack: the Web Payments SDK (an embeddable card form for a PWA), the Payments API, and the interlocking Catalog / Orders / Inventory APIs. The Catalog API auto-updates stock for item variations; the Orders API itemizes purchases, calculates totals/taxes, confirms payment, tracks fulfillment; the Inventory API decrements stock in real time when an order completes. ([Square Developer](https://developer.squareup.com/us/en), [Orders API](https://developer.squareup.com/docs/orders-api/what-it-does), [Inventory API](https://developer.squareup.com/docs/inventory-api/how-it-works))

**Pricing (2026, corroborated across four independent 2026 sources; Square's own pricing page did not render to automated fetch -- verify on squareup.com/pricing before publishing).** Square **raised the free-plan online card rate from 2.9% + 30 cents to 3.3% + 30 cents effective Jan 13, 2026** -- now the highest free-tier online rate of the majors.

| Plan | Monthly | Online card | In-person | Keyed-in |
|---|---|---|---|---|
| Free | $0 | **3.3% + 30c** | 2.6% + 15c | 3.5% + 15c |
| Plus | $49/location | 2.9% + 30c | 2.5% + 15c | 3.5% + 15c |
| Premium | $149/location | 2.9% + 30c | 2.4% + 15c | 3.5% + 15c |

([NerdWallet](https://www.nerdwallet.com/business/software/learn/square-fees), [merchantinsiders](https://merchantinsiders.com/blogs/square-fees/), [posusa](https://www.posusa.com/square-fees-pricing/))

**Data ownership.** Under GDPR the *seller* is the data controller and retains ownership; Square provides an export and a GDPR dashboard. **But the data physically lives on Square's infrastructure** -- sovereignty is contractual and export-based, never structural. Card-on-file export to a third-party processor takes up to **two weeks** plus manual verification ([Square card export](https://squareup.com/help/us/en/article/7871-export-card-on-file-to-third-party-payment-processors)) -- a real lock-in friction.

**Dropshipping.** None native. Square is payments/POS/catalog; the vendor-sourcing layer is yours to build regardless.

**Verdict for PoeTech.** Viable as a *payments-only* rail, but it adds nothing toward sovereignty or dropshipping over Stripe, and its free-tier online rate is now the most expensive of the majors. It owns the customer relationship in a way that sits crosswise to `DATA-AS-EMPOWERMENT-NOT-EXTRACTION.md`.

#### Path 2 -- Shopify / WooCommerce / BigCommerce (vendor e-commerce platforms)

**Shopify (2026, verified directly from [shopify.com/pricing](https://www.shopify.com/pricing)).** Basic $39/mo ($29 annual), Grow $105 ($79), Advanced $399 ($299), Plus from $2,300. Shopify Payments online rate 2.9% + 30c on Basic, down to 2.5% on Advanced. **The lock-in mechanism is the third-party-gateway surcharge: use Stripe instead of Shopify Payments and Basic charges an *extra* 2.0% on top of Stripe's own fee** (1.0% on Grow, 0.6% on Advanced). The richest dropshipping ecosystem of the three (DSers, AutoDS, Zendrop, Spocket, Syncee). Headless via the Storefront API + Hydrogen lets a custom React front end run while Shopify stays the backend. **Sovereignty problem:** customer/order data lives on Shopify; the gateway surcharge actively penalizes using your own processor. Structurally opposed to the sovereignty requirement.

**BigCommerce (2026).** Standard $39/mo ($29 annual) through Pro $399 ($299), with **annual GMV caps** (Standard $50K, Plus $180K, Pro $400K) that auto-upgrade the plan when trailing-12-month sales exceed the cap ([elogic](https://elogic.co/blog/bigcommerce-pricing/)). Zero added transaction fee if you use a pre-integrated gateway. Strong API story -- but "open SaaS" means API access to a proprietary platform, not source you can run on your own box ([wpbundle](https://www.wpbundle.com/guides/bigcommerce-headless-vs-woocommerce)). Fails sovereignty; the GMV cap is a hidden cost escalator.

**WooCommerce.** Open-source WordPress plugin -- free core, self-hosted, no revenue fees, no forced upgrades. The only one of the three that is *structurally* sovereign. **But it is a PHP/WordPress stack**, a poor fit for the Node/React PoeTech stack, and would mean operating a WordPress install on the NAS.

**Verdict for PoeTech.** None of the three SaaS options meet structural sovereignty. WooCommerce does but on the wrong stack. This category is where the sovereign open-source engines (Path 3) win outright.

**Why MedusaJS v2 is the fit.**
- **License: MIT.** Full ownership, no per-sale fee, no GMV cap, no feature paywall, no lock-in.
- **Stack alignment.** Node/TypeScript backend + Postgres primary store + Redis for the v2 workflow engine, cache, and event bus -- both Postgres and Redis are mandatory for v2 in production ([railway/medusa](https://railway.com/deploy/medusa)). Maps directly onto the existing PoeTech Postgres/Supabase layer + a Redis container on the NAS.
- **Marketplace / multi-vendor is native.** Medusa v2's module system models a marketplace with a custom Marketplace Module: `Vendor` and `VendorAdmin` data models, Vendor-to-Product and Vendor-to-Order module links (pivot tables, no hard coupling), a custom `"vendor"` actor type for auth, and workflows that split a parent order into vendor-specific child orders ([Medusa vendors recipe](https://docs.medusajs.com/resources/recipes/marketplace/examples/vendors), [multivendor guide](https://medium.com/@igorkhomenko/building-a-multivendor-marketplace-with-medusa-js-2-0-a-dev-guide-f55aec971126)).
- **The vendor-swap-with-audit-trail requirement is native.** Custom modules + workflow compensation functions + order metadata + the event bus are exactly the seams the requirement needs (Section 3.3).

**The honest deployment caveat (critical, stated up front).** **The Medusa backend cannot run on Vercel.** It is a persistent Node server, not a serverless function, and must run on an always-on host ([Medusa deployment docs](https://docs.medusajs.com/resources/deployment), [GitHub #4377](https://github.com/medusajs/medusa/discussions/4377)). **This is fine for PoeTech**: the **Synology NAS runs the Medusa backend as a Docker container** (always-on, no serverless timeout), Postgres + Redis as sibling containers, and **Vercel hosts the React/PWA storefront** that reaches Medusa over the same-origin rewrite pattern already in use (`project_n8n_same_origin_rewrite` -- the `/n8n` rewrite; a parallel `/store` or `/commerce` rewrite to the NAS Medusa container). n8n (also on the NAS) subscribes to Medusa's event bus for vendor scoring, swap automation, and the audit log -- which is exactly the `AI-FOUNDATION-INTERNAL-OPERATIONS.md` posture ("anything that is a click today should be an API call tomorrow, called from a workflow").

### 3.2 Dropshipping vendor model -- the swap-and-audit requirement

Darrell's requirement, verbatim: *"we add any vendors we want based on what and who does the best and whenever they change we want the ability to keep records and we can change the vendors to reflect our new found reality also consistently looking for better vendors in our spaces."*

This is a textbook case for the **Adapter Pattern** -- a vendor abstraction layer that normalizes heterogeneous supplier APIs into one internal interface, whose explicitly-named benefit in the literature is *"reliability through seamless provider switching"* ([zigpoll](https://www.zigpoll.com/content/what-are-the-key-technical-challenges-when-integrating-multiple-supplier-apis-in-a-dropshipping-platform-to-ensure-realtime-inventory-and-order-tracking), [adapter pattern for vendor-agnosticism](https://medium.com/@jescrich_57703/harnessing-the-adapter-pattern-in-microservice-architectures-for-vendor-agnosticism-debc21d2fe21), [flxpoint](https://flxpoint.com/blog/dropshipping-api-integrations-explained)).

**The aggregators and direct-supplier APIs surveyed:**

| Tool | Reach | API | Notable |
|---|---|---|---|
| **AutoDS** | 25+ suppliers, 500M+ products (incl. AliExpress, CJ) | Yes -- automation API | Broadest multi-channel ([AutoDS API](https://www.autods.com/api/)) |
| **Spocket** | US/EU suppliers | Integration-based | Faster shipping, branded invoices |
| **Modalyst** | Eco/independent brands | Integration-based | Niche/sustainable |
| **Doba** | Catalog aggregator | Real-time inventory + price sync | Multi-marketplace ([doba](https://www.doba.com/blog/find-products-and-suppliers/finding-suppliers/doba-vs-autods-2026-which-dropshipping-platform-actually-fits-your-business-39546)) |
| **Syncee** | Global B2B | Flexible | International sourcing |
| **CJ Dropshipping** | Direct supplier | **Free API** (products, orders, payments, logistics, warehousing) + an MCP server | Custom-store-friendly ([CJ Docs](https://developers.cjdropshipping.com/), [CJ MCP](https://developers.cjdropshipping.com/en/api/api2/mcp.html)) |
| **AliExpress / Alibaba Open Platform** | Direct supplier | Product info, publish, order mgmt; community SDK | Largest catalog ([AliExpress Open Platform](https://open.aliexpress.com/), [ae_sdk](https://github.com/moh3a/ae_sdk)) |

**The vendor abstraction layer, concretely (Medusa custom module on Postgres):**

1. **A `VendorAdapter` interface** every supplier must satisfy: `searchProducts`, `getInventory`, `placeOrder`, `getTracking`, `getPricing`.
2. **One adapter per supplier** (CJAdapter, AliExpressAdapter, AutoDSAdapter...), each translating that supplier's API quirks into the common interface.
3. **A vendor registry** in Postgres mapping each product/SKU to its current active vendor(s) -- enabling swap-without-code-change.
4. **An append-only `vendor_change_log` audit table** -- `(product_id, old_vendor, new_vendor, reason, performance_snapshot, actor, timestamp)` -- written on every swap. Append-only + on your own Postgres = sovereign and tamper-evident by design. **This is the direct answer to "keep records ... change the vendors to reflect our new found reality."**
5. **A `vendor_performance` table** fed by order outcomes (fulfillment time, defect/return rate, stock-out rate, margin) -- the metric basis for "swap freely based on who does the best." n8n runs the scheduled scoring and auto-flags underperformers ("consistently looking for better vendors").
6. **Event-bus hooks** so a swap emits an event; n8n turns it into a digest entry + family-voice notification.

This layer sits *between* Medusa's order workflow and the suppliers, so the rest of the system never knows or cares which vendor fulfilled a line item. Vendors become a configuration fact, not a code dependency -- which is precisely Darrell's "we add any vendors we want."

### 3.3 Payment processing for the sovereign build

A sovereign storefront still needs an external payment rail (card networks, PCI scope, chargebacks are not things to self-host). The comparison:

| Processor | US online rate (2026) | Marketplace/split | Customer relationship |
|---|---|---|---|
| **Stripe** | 2.9% + 30c | **Stripe Connect** -- the marketplace reference; separate charges + transfers | **You own it** (Stripe is infra) |
| Square | 3.3% free / 2.9% paid | Limited | Seller is controller |
| PayPal | 3.49% + 49c checkout | Weaker split | PayPal-branded |
| Adyen | interchange++ (~0.6% + $0.13), enterprise; EUR500-5,000 setup | Adyen for Platforms | You own it |

([Stripe pricing](https://stripe.com/pricing), [Stripe Connect](https://stripe.com/connect/pricing), [PayPal fees 2026](https://www.paypal.com/us/business/paypal-business-fees), [Adyen vs Stripe](https://www.nerdwallet.com/business/software/learn/adyen-vs-stripe))

**Recommendation: Stripe + Connect.** The marketplace reference implementation; first-class Medusa plugin; keeps the customer relationship with PoeTech (Stripe is infrastructure, not a brand in the funnel -- important for `feedback-distinguish-data-from-brand`); supports the split-payment model dropshipping needs. Connect specifics: ~$2/mo per active connected (vendor) account, 0.25% + 25c per payout, and **you may not pass dispute fees to connected accounts** ([Stripe Connect charges](https://docs.stripe.com/connect/charges)). Card data never touches the NAS (Stripe Elements/hosted fields keep PCI scope minimal). Adyen beats Stripe on rate only at very high volume and carries setup + monthly platform fees -- not worth it at MVP/growth scale. PayPal is priciest and weakest on ownership.

### 3.4 Cost analysis at three scales

**Assumptions:** $50 average order value, all card volume, chargebacks excluded from the base model. Illustrative models built from the verified rate cards above -- not vendor quotes.

| | MVP (~10 orders/mo, $500 GMV) | Growth (~500/mo, $25K GMV) | Scale (~10K/mo, $500K GMV) |
|---|---|---|---|
| **Square** | ~$19.50/mo | ~$924/mo | ~$17,649/mo |
| **Shopify (own gateway)** | ~$56.50/mo | ~$914/mo | ~$15,899/mo |
| **Shopify + Stripe surcharge** | ~$66.50/mo | +~$250/mo | +~$3,000/mo |
| **Sovereign Medusa + Stripe** | **~$20-35/mo** (NAS sunk) | **~$760-820/mo** | **~$14,500-15,500/mo + infra** |

**Where cost lives.**
- **At MVP, subscription dominates.** Shopify's $39 is 2x the entire processing cost. Square Free and sovereign-on-existing-NAS are near-free. The sovereign option wins because **the NAS infra is already sunk.**
- **At growth and scale, per-transaction fees dominate completely.** At $500K GMV, ~$14.5K of every option is just the ~2.9% card fee; subscription differences become rounding error. **The only real lever at scale is the processing rate** -- which is why Shopify's *extra* 0.6-2.0% third-party-gateway surcharge is a meaningful penalty the sovereign build entirely avoids.
- **The sovereign build's structural advantage:** it pays Stripe's rate and nothing else -- no platform subscription, no GMV cap, no gateway surcharge. The trade is engineering time, not recurring rent.

### 3.5 Recommendation, tier label, and the five-test result

**RECOMMENDATION: Build sovereign.** MedusaJS v2 backend on the Synology NAS (Docker container) + React/PWA storefront on Vercel + Stripe Connect for payments + a custom vendor-abstraction-layer module + an append-only `vendor_change_log` audit table + n8n for vendor scoring/swaps/digests. Sequence it lean (Section 6) -- do **not** build the whole marketplace before the first sale.

**Sovereign-mesh tier label** (per `project-sovereign-mesh-mvp-pragmatism`; the tier model lives in the agent-memory workspace, so the working interpretation used here is stated explicitly: **Tier 1** = fully sovereign on the NAS; **Tier 2** = hybrid-sovereign, NAS + cloud API with redaction; **Tier 3** = vetted external vendor under a data-processing boundary; **Tier 4** = full external SaaS, data leaves):

- **The commerce engine + product/order/customer/vendor data + audit log: Tier 1 (fully sovereign on the NAS).** Every row lives in PoeTech's own Postgres.
- **The payment rail (Stripe): Tier 3 (vetted external vendor, unavoidable).** Card networks and PCI scope cannot be self-hosted responsibly; Stripe is the narrowest-data, customer-relationship-preserving choice. Only payment-method data crosses, and via hosted fields it never touches the NAS.

This is the honest hybrid: **the spine is Tier 1, the rails the world forces on commerce (payments, suppliers) are Tier 3 and swappable.** Nothing is Tier 4.

### 4.3 Reaction model -- "like / love / not-like" without a pile-on

Darrell asked for *"like love not like"* -- deliberately gentler than a hostile downvote. The UX research strongly supports this instinct:

- A widely-cited community-design argument: **never add a pure "dislike" button** to a community platform; like-and-dislike voting produced measurable user discomfort even on platforms that use it ([Julia Warmuth](https://medium.com/@juliawarmuth/why-you-never-should-put-a-dislike-button-to-a-community-platform-58d7ff734d24)).
- Twitter's own research distinguished a *downvote* (content-quality signal) from a *dislike* (personal preference) and worried downvotes could harm mental health **because the platform lacks anonymity** -- visible negative signal on *attributed* posts is the harmful variable ([TechCrunch](https://techcrunch.com/2021/03/24/twitter-is-exploring-the-use-of-facebook-style-emoji-reactions/)). PoeTech posts are attributed, so this warning is directly load-bearing.

**Design implication.** Model `reaction_type ∈ {like, love, not_like}` as a single join row per (user, target) with `UNIQUE(user_id, target_id)` (the richer-enum version of Lemmy's binary `actions` table). **Critically: `not_like` must NOT subtract from a public score, trigger auto-hide, or demote ranking.** It is a gentle, private/aggregate-only affect signal -- "this doesn't sit right with me" -- not a downvote that buries the author. This satisfies Darrell's "not like" precisely while honoring 2 Timothy 2:24 (not quarrelsome) and the Father's Business (don't bury the seeker over a reaction). The bite goes on the *lie* via moderation, never on the *person* via a pile-on tally.

### 4.4 Moderation framework -- truth-grounded, intent-aware, human-in-the-loop

This is the heart of Part B. The requirement: filter the *doctrines of demons* (name and refuse the lie) **without silencing the honest seeker** (lose none -- John 6:39). The wrong tool here is fatal to the mission.

**The wrong tool: a context-blind toxicity score.** Perspective API (Jigsaw) scores each comment in isolation, ignores intent, and **systematically over-flags** -- at low thresholds a false-positive rate near 1.0 on incivility data, and it misreads strong-but-faithful language and even non-English text as toxic ([Sage / Gervais 2025](https://journals.sagepub.com/doi/10.1177/1532673X241309627), [arXiv 2312.12651](https://arxiv.org/abs/2312.12651)). For a faith platform that must protect sincere doubt and pointed-but-loving correction (Ephesians 4:15), a blunt toxicity score would silence the very seekers the Father's Business pursues. **Do not use Perspective as the primary gate.**

**The right pattern (n8n-native, post-moderation with a fast pre-gate + reactive flagging):**

1. **On submit,** the comment/link is written `status = pending` -- visible only to the author.
2. **n8n workflow fires** (this is the Quality Gatekeeper, `wf36`, extended to user content -- per `PERPETUAL-PIPELINE-HEALTH.md` Role 10, currently L5 on the fix-master-list):
   - **Reflex filter:** the **free OpenAI Moderation API** (13 categories: hate, violence, sexual/minors, self-harm, etc.) blocks clear hate/violence/CSAM instantly ([OpenAI docs](https://developers.openai.com/api/docs/guides/moderation)).
   - **Worldview classifier:** a **custom LLM classifier** (the per-industry sovereign LLM team, L9; Word-first/Body-undivided per `project_non_denominational_word_first_body_undivided`) prompted against the truth-grounded standard. Unlike Perspective, an LLM with a careful system prompt reasons about *intent and context* and can distinguish "honest seeking question" from "bad-faith attack" ([ICWSM moderation study](https://kumarde.com/papers/llm-contentmod.pdf)). It returns `{decision: approve | warn | hold, rationale, scripture_anchor}`. **This is where the 4th-vs-3rd-dimensional frame lives** -- the system prompt encodes Colossians 3:1-2, Galatians 3:28, the Word-first posture, and the krino-not-katakrino rule.
3. **Warn-then-edit** (the Coral Talk pattern) on borderline content: surface the rationale + a Scripture mirror, let the user revise before it posts. This is the Council Chamber's Mirror section applied to discussion -- the verse is offered, not weaponized ([Coral toxic-comments docs](https://legacy.docs.coralproject.net/talk/toxic-comments/)).
4. **Hold -> human-in-the-loop queue** for `hold` decisions; a family/moderator (governance per `GOVERNANCE-EXECUTION-ADVISORY.md`) approves or rejects. LLM classifiers augment, never replace, human judgment ([AVID](https://avidml.org/blog/llm-guardrails-4/)).
5. **Reactive flags** post-publish feed the same queue.

**How this enforces "disrespect the lie, honor the person":** the classifier is prompted to flag the *pattern* (the doctrine, the lie, the 3rd-dimensional framing) and to draft a *gentle, Scripture-anchored correction* aimed at the person's understanding -- never a condemnation of the person. A flagged comment does not vanish silently; the seeker gets the Word held up as a mirror and a chance to engage. The bite is on the argument (2 Cor 10:5); the warmth is on the soul (2 Tim 2:25).

### 4.5 Privacy-default visibility -- community-shared link, PIN-locked private note

Per `project_pin_optional_community_default` (the comment/share visibility model -- in the agent-memory workspace; the in-repo D21 fix already ships a "Testimony Diary PIN-locked entry point," confirming the pattern is live):

- A **`visibility` column** on every content row, defaulting per type: a *submission* (shared link + take) defaults to `community`; a *personal note / annotation* defaults to `private` (PIN-locked, owner-only).
- Enforced at the database layer with **Postgres Row-Level Security (RLS)** -- a policy keyed on `current_user = creator OR (visibility = 'community' AND user is member) OR visibility = 'public'`. RLS filters rows *before they leave the database*, so a private note stays locked even if an app query forgets to filter ([Postgres RLS guide](https://www.codemancers.com/blog/row-level-security-in-postgres)). This is the structural guarantee that satisfies `DATA-AS-EMPOWERMENT-NOT-EXTRACTION.md`'s "deletion is immediate and verifiable / opt-in per stream / audit log on every access."

### 4.6 Federation -- stay walled (no ActivityPub at launch)

Federation (ActivityPub / Lemmy / Mastodon / Bluesky AT Protocol) pushes the community's data out to servers PoeTech does not control. Lemmy is the cautionary example: **votes are not private under federation** (individual votes are broadcast over ActivityPub to other instances), and **instance moderation settings do not federate** -- Lemmy's downvote-disable toggle did not stop downvotes arriving from remote instances ([join-lemmy votes](https://join-lemmy.org/docs/users/03-votes-and-ranking.html), [Lemmy #2124](https://github.com/LemmyNet/lemmy/issues/2124)). Federation would directly undercut two PoeTech requirements: user data never leaving PoeTech's control, and a moderation standard PoeTech can actually enforce. **Launch walled.** Federation is a later, optional, *outbound-only* consideration (publishing select content to the fediverse), never the default ingestion path.
